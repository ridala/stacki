Existing Astro setup tasks

Help people open an existing Astro site and understand what Stacki can edit. Scan it without changing the site, suggest folder settings, and let the person review any changes before saving them.

This is an implementation checklist based on a source audit. No live project was supplied. A later, optional migration is a separate release stage and needs its own approval and recovery plan.

Decisions

Read-only first
Offer a setup scan before preview starts. The scan, Skip and Close leave project files alone and install nothing. Starting preview is a separate action that can run project code. Bound files, paths, bytes, evidence, time, and output, and report incomplete or uncertain results. The scan and folder settings work without an agent.
Review folder settings
Suggest a mapping, show evidence and effective discovery counts separately for Desktop and Studio, and save only after review. Preserve existing custom values, explicit empty lists, unknown keys, and CMS settings. Show when a restart is required. A mapping alone must not change public routes, source, or configuration.
Support boundaries
Distinguish Desktop with local Studio, standalone Studio drafts, and hosted Studio. Ship each only after its own path, role, sync, and publishing behavior is proven. Label unsupported or computed configuration as unverified.
Optional assistance
Reuse the audit interface and existing agent task contract. Provide a built-in draft and copy handoff. External agents can produce reviewable patches. Do not add a provider or API. The user reviews the selected, project-relative evidence before sharing it. Exclude credentials and unrelated content. Treat project data as data, never agent instructions.
Migration
Defer source moves to a separately released, explicitly approved plan. Treat CLI and MCP dry-run output as a proposal. Require the user's approval to apply it. No automatic source write, push, or deployment.

What the source audit found

  • Desktop classifies picked and dropped folders. Recent projects go straight to the project loader. The File menu uses a separate Astro check. The loader currently starts preview before the scan completes, and the scan can update local Git exclusions. Add a read-only entry before that sequence and keep the plain HTML copy flow separate. Folder opening · File menu · Project loader · Project scan
  • The scan derives pagesFolder from literal srcDir. Computed settings fall back and raise a warning. Config extension precedence differs across scan, Desktop preview and Studio workspace scripts. Page creation follows the discovered directory, while rename, settings, bulk operations, templates and preview markers need an audit for fixed src/pages assumptions. Config scan · Studio workspace
  • Studio discovery, page addresses, editor navigation, routes, path bounds and role policy assume src, public or src/pages. Live sync and the Git publish snapshot have their own source allowlists. Hosted support needs a separate gate. Project server · Page address · Sync paths · Publish inventory
  • Version 1 folder metadata has literal src, public, and styles roots. Explicit maps can narrow Studio's broader discovery. Use the existing witnessed metadata save and stale re-scan behavior. Folder contract · Metadata contract · Desktop metadata · Studio metadata
  • The audit UI, static and rendered audits, site runner, page-settings link relocation, fixture head, robots and sitemap, and shadcn starter SEO provide evidence for the initial audit. Trace their callers before implementation. Audit runner · Agent task · Starter checklist · Contracts (especially project paths, metadata, Studio and publishing).

Tasks in implementation order

T1. Establish the baseline

P0 · Start here. Files include folder opening, scan, preview, Studio workspace and contracts.

Trace every entry point and config extension precedence against supported Astro versions. Inventory page create, rename, settings, bulk, templates, preview markers and Studio paths. Record observed versus inferred behavior, existing errors, role restrictions and restart requirements. Define explicit limits and a shared configuration precedence only after comparing Astro behavior.

Acceptance. Fixtures reproduce the current differences and identify unsupported cases. Unreadable, conflicting, computed and absent config must produce an honest result, never execute config or silently claim support.

T2. Define scan and recommendation contracts

P0 · Dependencies T1. Files include projectFolders, shared IPC and feature boundary parsers, scan modules and contract tests.

Define a report with the selected root, configuration evidence, proposed metadata changes and status per editor and operation. Use Astro imports, layout references and configured paths as evidence. Folder names alone can suggest candidates for review. Leave mixed folders and uncertain classifications for the user to resolve. Use the existing catalog rules to show which files a proposed change would add or remove. Parse inputs and outputs at the shared boundary. Resolve paths within the project and reject escapes, unsafe symlinks and excessive traversal.

Acceptance. A scan is read-only, bounded and repeatable. Partial scans state what they omitted. Permission errors, malformed files, cycles, oversized projects and cancellation leave no writes or dependency installation.

T3. Review and save mappings

P0 · Dependencies T2. Files include project metadata handlers and bridges, folder settings UI, audit UI and localization.

Offer Set up this site from the existing Astro open flow, and Check folder setup in Settings → Folders. Show proposed values, affected files and each editor's effective counts before and after. Provide actions to save the selected settings, skip setup, or review unresolved items. Reuse the witnessed metadata save. On a stale revision, re-scan and require a fresh review. Preserve unknown keys, CMS, custom mappings and explicit empty values. Make save idempotent and report restart requirements.

Acceptance. Opening the setup report or skipping changes no project bytes. Saving changes only approved metadata and a second save leaves the file as it was. A concurrent edit, failed write or cancellation cannot overwrite newer settings. Verify focus return, keyboard access, screen reader status messages, long translations and right-to-left layout.

T4. Align local editor paths

P0 · Dependencies T1, T2. Files include Desktop page operations and preview, plus the Studio project server, page address, navigation, routes and role policy.

Trace the resolved source and pages paths through each operation and validate them at boundaries. Reconcile config selection with preview and workspace startup. Keep role restrictions and project path bounds intact. For a configuration that cannot be resolved safely, disable affected operations with a useful explanation.

Acceptance. Desktop and local Studio agree for supported fixtures, including create, rename, settings, bulk, templates and preview. Unsupported, stale, escaped or missing paths fail safely without writing elsewhere.

T5. Add optional agent handoff

P1 · Dependencies T2, T3. Files include audit UI, agent task contract and tests.

Build a bounded draft from selected evidence and warnings. Include project-relative paths, the observed restriction, the requested outcome and the checks the agent should run. Show what will be copied or shared and allow review and removal. Run the existing CLI checks where available. Give an external agent the draft for a patch review. Keep apply approval with the user.

Acceptance. Deterministic setup works without AI. Tests cover secrets and unrelated content exclusion, hostile project text, truncation, cancellation and accessible copy feedback.

T6. Prove standalone and hosted Studio separately

P1 · Dependencies T4. Files include Studio project server, sync paths, publish inventory, role policy, bundle manifest and tests.

Trace draft and hosted reads, edits, sync and publishing for each supported root. Include shared source in the assembled Studio bundle. Check permissions and path validation at every boundary. Do not advertise hosted support for roots that sync or publish omit.

Acceptance. Standalone draft and hosted tests prove the same approved files survive round trips under each role. Missing files, path escapes, conflicts and denied roles produce visible failures without partial publication.

T7. Optional migration release

P2 · Dependencies T3, T4, T6 and the route evidence below. Files include migration planner, metadata and recipe handlers, tests and release documentation.

Plan in an isolated checkout or draft. Bind the exact approved plan to project identity, revisions and role. Reject stale approval. Detect collisions and ambiguous imports, routes and references. Stage and verify writes, preserve config, integrations, assets, imports and lockfile, and update page metadata keys plus recipe keys and nested component references. Provide rollback, undo and recovery after interruption.

Acceptance. A person can inspect and approve the precise plan, verify every staged change and recover the original on failure. No automatic source write, push or deploy occurs. Changes to scripts, lockfile or deployment require explicit approval.

Fixture matrix

Run the relevant cases at each task boundary. Record supported Astro and integration versions, operating system and package manager. Exercise a nested monorepo and an installed CLI alongside source tests.

Case Required evidence
Default, configless and literal custom directories Scan, counts, page operations and preview agree. The scan leaves project files alone.
Computed, conflicting extensions, unreadable or invalid config Tests pin config precedence. The report shows uncertainty and blocked operations.
Nested workspace, symlinks, outside paths and size limits Containment, traversal limits, cancellation and partial evidence are verified.
Existing metadata, CMS, unknown keys, custom and empty lists Compare both editors' effective counts. Saving preserves unrelated values and is idempotent.
Static, dynamic, nested, localized, generated, SSR and CMS routes Show the tested behavior and label unresolved runtime routes as unverified.
Stale edits, collisions, permissions, interrupted writes and recovery Verify that conflicts protect existing work, publish stays atomic, and rollback and retry work.

Route and SEO preservation

Mapping-only setup must leave public behavior, source and config unchanged. SEO preservation is independent of ranking, marketing, or automatic rewriting. For a migration, capture before and after evidence for source, preview and production. Use observed responses to verify production host and CDN behavior independently of the local build.

  • Build a route matrix with status and Location, legacy aliases, query strings, base paths, trailing slashes, casing and encoding. Require direct 301 or 308 redirects to equivalent targets, or real 404 or 410 responses where there is no equivalent. Verify redirect chains and retain redirects generally for at least one year.
  • Save a route inventory using available sitemap, link, Search Console or access-log evidence. Record a disposition for every in-scope URL. Compare HTTP headers, raw HTML and rendered metadata. Preserve deliberate canonical and indexing choices, titles, descriptions, headings, social cards, structured data and asset references. Verify locale alternates reference themselves and each other, and preserve the existing default reference where one is present.
  • Fetch /robots.txt at the production origin. Parse each sitemap index and child sitemap and verify final, canonical, indexable URLs. Check both HTML robots directives and X-Robots-Tag. Require authentication for private staging. If staging must be public, serve noindex on crawlable responses so search engines can read it. Keep staging URLs out of production metadata, and verify temporary exclusions are removed from intended indexable pages at launch.
  • Compare prerendered parameter and catch-all routes against the build output. Use an authoritative inventory or explicitly reviewed valid and invalid samples for server-rendered and CMS routes. Record unresolved middleware, adapter, integration and CDN behavior. For actual URL moves, replay the approved map against production, submit the sitemap and monitor indexing, clicks and errors in Search Console. Approve deployment separately, including any Git push that can trigger it.

Official references include Google site moves · Redirects · Block indexing · Canonical URLs · Sitemaps · Localized versions · Astro configuration · Astro routing · Astro sitemap.

Release gates

  1. Ship the report and folder settings after T1 through T3 pass. Prove mapping-only behavior with byte and public route comparisons. Keep unsupported operations visible in the report. Expand local support after T4 passes, and enable agent handoff after T5 passes.
  2. Run new shared contract and negative boundary tests, Studio bundle shared-source manifest checks, and astro-studio check-project <project-directory> using the installed CLI. Fix missing paths, invalid slots and cyclic recipes together.
  3. Open a pull request and let GitHub Actions run the repository checks on its current commit. Resolve failures on the branch before release.
  4. Document supported versions, limitations, role boundaries, restart behavior, recovery and release procedure. Gate standalone and hosted support separately with T6 evidence.
  5. Release migration only after T7, the route matrix, approved plan and production deployment review pass. Record remaining remote verification and post-release monitoring.
