Audit and decisions

Desktop PageSettingsDesktop orders title, description, image, ogImage, canonical, noindex, and keywords ahead of other layout props and edits them through InstancePropFields. A matching name does not prove that a prop controls an SEO tag. The shared PageSettingsDialog supplies section slots. Studio's PagesPanel passes a rename-only host to that dialog. Studio already writes layout attributes through its Properties inspector.

useLayoutMetadata and framePageText provide preview text with social metadata priority. They are not a complete representation of the actual head. The rendered canonical check uses a dummy base and compares paths. The crawl-file check looks for sitemap and robots presence. Neither proves the published URLs are correct. Add separate head facts and treat unavailable or stale preview results as unknown.

Studio Settings, useDocument, and clientPolicy are starting points for guarded collaborative writes, role and selection checks, and Yjs undo. Review the source-document gates as well as client policy; UI visibility alone is not authorization. The current Studio guard checks the canvas selection. SEO writes must check the actual layout target, including when the dialog opens for a different page. Read the shared contracts before changing cross-process data or bridges.

The shadcn starter has head markup in shadcnStarterContent and a sitemap with two hardcoded gallery routes in shadcnStarterSite. External create-lumos and vanilla Astro are separate creation paths. The Studio site fixture includes project constants, BaseLayout, BaseHead, Astro sitemap and robots. astroConfigText reads configuration as text; computed or opaque values do not establish a safe writable owner.

Desktop's publisher uses a snapshot build. Studio uses a normal Astro build; its demo bake overrides the base and inserts noindex. Private Studio drafts and published output have different visibility. Preview and draft origins must never become public canonicals. The Astro Copy path preserves extension URLs and can emit redirect documents. The Apps API can support optional tooling, but general file writes require code-edit access and lack Studio undo. Use the native editor paths for this contribution.

1. Define ownership and facts

Inventory static Astro source, rendered head and site configuration separately. Specify a bounded shared contract with declared values, actual rendered facts, provenance, unsupported and unknown states. Capture actual title, description, canonical, robots and explicit social tags independently, including duplicates and invalid placement. Bind each response to the project, source file, concrete preview route and navigation generation and the rendered source revision or refresh generation. One template file can have several routes. Invalidate on navigation, save, undo, and remote source changes. Keep facts unknown until the expected render arrives, even when the route stays the same. A generic image prop provides no evidence of social image semantics.

Show read-only facts where ownership is unknown. For the first release, support concrete .astro routes with one resolvable layout instance and an explicit author mapping. Implement the mapping as a bounded project-authored JSDoc annotation on supported layout props. Define its accepted semantic names, require one field per role, and reject duplicate roles, incompatible types, unresolved imports and ambiguous targets. Prototype the annotation with the existing prop inference on the fixture before exposing edits. Preserve unmarked projects' current Properties workflow.

Model editable literal, inherited default, bound and unsupported values separately. Read only bound values and props shadowed by spreads in the first release. Reset an optional literal override by removing its attribute if the existing layout can supply the default. Required props stay required. A later binding override needs an explicit author-owned fallback representation or undo of the exact patch. Reload must never require reconstructing a lost expression from a preview value.

Parse boundary data in shared/ or the matching existing parser before use. Bound strings, tags, duplicate observations and preview requests. Keep raw HTML and script out of the contract. Use source-located edits and expected revisions, preserve unrelated bytes, and report stale or unsupported operations before writing. The Astro project remains the only store for metadata values.

Acceptance: A contract test covers valid, malformed and bounded facts, duplicate tags, stale replies, unknown preview, literal, bound and ambiguous ownership. An audit shows declared and rendered values separately, with reasons for read-only fields. No source changes occur from inspection. Delay an old same-route head reply until after saving a new title. The reply must never replace the new facts.

2. Desktop page settings MVP

  1. Add SEO before Layout props in Page settings. Reuse the current layout field editors and edit handlers. Use the full schema to classify extra attributes before deciding which fields each section renders, so moved fields appear only once. Page rename, duplication, homepage change and deletion keep their existing handlers.
  2. Support page title, meta description, social image and alt text, canonical override and noindex when the author mapping exposes them. Put canonical and indexing controls last. Show Use site default for an optional unset or resettable field, and make a denied or bound field read-only with a reason. For optional noindex, offer three distinct states: inherit by removing the attribute, write explicit true, or write explicit false. Classify bare booleans and exact {true} or {false} expressions as literals. Leave computed expressions, unsupported formats and unknown owners inspectable.
  3. Show the actual title, description, canonical and link card separately from authored fields. Label a search or social card approximation as a preview. An unavailable preview leaves the source field visible and the output unknown. Use the shared message catalog, keyboard focus, existing asset picker and modal controls. Keep long URLs and translations within the dialog. Validate absolute HTTP(S) canonical overrides without credentials or fragments. Resolve local social assets with Astro's public base and the configured production origin. Keep server-side preview queries scoped to the active project; avoid fetching arbitrary remote URLs on the user's behalf.
  4. Use the ordinary editor save and undo path. Revalidate file, layout identity and revision when applying the patch. A failed write keeps the draft visible and emits an actionable error. Run the linked audit for unsupported output rather than injecting fallback tags.

For indexable pages, audit title, description, head validity, canonical origin and URL, robots and social declarations. For explicitly noindex pages, suppress recommendations that presume indexing while still reporting malformed or conflicting directives. Do not add a meta keywords field as a Google ranking recommendation. Do not impose fixed title or snippet limits; Google chooses display text and truncation varies.

Acceptance: Literal edits round-trip through source and build. Undo restores the exact source, reset removes an optional override, and bound or unsupported layouts remain read-only with no filesystem changes. Preview navigation cannot display another page's facts. Audit recognizes noindex exemptions and distinguishes the public origin from preview. Save, reopen, build and undo all three indexing states on a route that defaults to noindex. Check the fixture's existing sitemap both when excluding and restoring a page. If a separately owned sitemap still lists a newly excluded or noncanonical page, or omits a restored indexable page, show the observed mismatch and preserve its configuration. Show unknown for a sitemap whose output cannot be checked.

3. Studio parity

Register shared files in shared-source.json and run npm --prefix studio run assemble. Edit canonical source and Studio adapters. Wire the dialog to the exact current source document and concrete route. Use attributeEdit and the existing collaborative document write path. Apply one deliberate edit as one local undo operation. Recheck role, document readiness, actual layout lock and revision before applying. Handle remote edits with the document's established conflict path.

Keep access within the existing page:layout authority in the first Studio release. Before enabling SEO writes, extend the server's document policy to reject protected SEO layout attribute changes from restricted roles, including changes via raw collaboration updates. The current Client comparison checks the layout name and surrounding bytes. An opening tag's attributes can change without changing either. Use the authoritative current source and check additions, removals and changes of protected attributes. Keep permitted child content edits functional.

Acceptance: Authorized users see and edit the same supported fields as Desktop. Read-only roles and denied source documents cannot write even through a forged collaboration update. Through the actual room, verify that a restricted role can still update child content, and that the room rejects a protected attribute mutation without changing the document. Concurrent editing, selection changes, stale replies, undo and redo preserve unrelated content. Private drafts are labeled and do not supply public canonical origins.

4. Starter support

Define explicit SEO prop semantics in the shadcn starter's own layout and head, including a specifically named social image. Generate valid head markup and an absolute canonical only when a verified public site URL exists. Replace the two-route sitemap assumption with a route inventory appropriate to the starter. Keep robots behavior consistent with the deployed host root. Examine the separate create-lumos and vanilla Astro paths; add support only where their generated source can safely declare the same ownership, and document any external generator limitation.

Use Astro's escaped markup for title and attributes. Verify that metadata changes do not break the existing JSON-LD output. For a complete managed Open Graph card, emit title, type, URL and a crawlable absolute image URL, alongside alt text when available. Align og:url with the canonical. Preserve existing twitter:* fields where the project uses them. Publish no automatic preview-host canonical or image URL when the public site URL is missing.

Acceptance: Fresh starters build with and without a configured public site, preserve custom source on reopen, and expose only declared fields. A newly added eligible route appears in the sitemap. Excluded routes stay out. Generated sitemap and robots agree with actual published URLs. Existing projects are never migrated merely by opening settings.

5. Explicitly adopted site settings

Add a project-level Settings / SEO section after the page editor passes its output checks. Start with detected public URL, base, trailing slash, output mode, sitemap and robots ownership. Link to the source when a value is computed, imported or produced by an existing integration. Keep route policy read-only in this contribution because changing base or slash policy can move every public URL.

For an explicitly managed project, support the public site URL and author-declared site defaults: site name, title template, fallback description, fallback social image and image alt text. The public URL belongs in Astro site. Defaults belong in the existing shared head or its declared constants. Define fallback precedence as an explicit page value, then the project's existing default, then omission when the field is optional. Apply the title template once. Support a managed sitemap and a robots sitemap reference only where each output has one clear owner.

Start adoption from a fresh read of the project. Adoption must identify exact source owners, show a reviewable change, and require an explicit user action. Support only safely editable literal configuration; computed, imported or ambiguous configuration stays read-only. Preview the exact file diff and every impacted route class. Re-read and compare all expected source revisions before applying edits. Use existing project containment and witnessed write patterns. If a second file write fails, compare each affected file to the exact bytes adoption wrote before attempting an atomic, witnessed restore. Preserve an intervening edit and report each file that needs recovery. Re-read affected files after recovery. If the host cannot enforce this compare-and-write guarantee, limit adoption to one-file edits. Return a conflict for changed sources, duplicate owners or unsupported config shapes.

Define one native owner for each output: Astro configuration for site and URL policy, the project's existing head for canonical and metadata, and an explicitly adopted sitemap or robots implementation for those files. Do not generate competing outputs. Managed sitemap entries must be public canonical URLs and exclude noindex, noncanonical, redirect, 404 and probe routes. Use real build output or an explicit route declaration, not guessed paths. A root /robots.txt belongs to the host even when the app is deployed under a base path; document deployment responsibility and do not assume a subpath file controls the host root.

Use the same route policy for managed head tags and sitemap filtering. noindex is a page directive and needs crawler access. A robots crawl block can keep crawlers from seeing the directive. Preserve independent nofollow and existing HTTP headers. Warn when a configured canonical or indexing directive conflicts with observable output. Sitemap generation should omit duplicates that canonicalize elsewhere and preserve intentional redirect aliases as redirects.

Acceptance: Adoption shows a diff and writes only approved owners; cancellation, conflict and unsupported config leave files unchanged. Force a failed second write with an intervening edit to the first. Keep the newer edit and report the recovery status. Builds cover root and subpath bases, trailing slash policies and .html output. Sitemap, canonical and robots are consistent with the public deployment, and demo bake noindex and base override do not leak into published configuration.

6. Dynamic routes, SSR, collections and i18n

  1. For statically generated dynamic routes, prototype with the Astro fixture and verify each concrete output from getStaticPaths(). Bind per-entry SEO to explicitly selected content schema fields through the CMS editing path. Label template-level defaults as affecting multiple URLs. Check removed entries, duplicate slugs, stable entry identity and draft entries.
  2. For Markdown and MDX, add a format-aware frontmatter path only where the layout is known to use the mapped values. Test comments, delimiters, existing expressions, bad YAML, and exact-byte preservation outside the changed fields.
  3. For real on-demand SSR, require a bounded author-provided route inventory or a deployment-specific sitemap endpoint. Validate true public requests with the production adapter and a request hostname distinct from the configured public origin. Probe HTTP robots headers and keep unavailable facts unknown.
  4. For localized pages, preserve each route's own metadata and canonical. Add alternates only from explicit route groups with absolute, reciprocal links including each page's own URL. Verify same-language canonicals where available and treat x-default as optional.

Acceptance: Fixture builds and deployed SSR integration tests exercise multiple routes, changed collection data, missing provider values, localized variants and failures. Unsupported providers remain untouched. Document cache, refresh and host responsibilities before enabling each integration.

Risk and effort: Desktop ownership and accurate rendered facts are high effort and high risk because source edits and asynchronous previews can corrupt or misrepresent state. Studio parity adds collaboration and authorization risk. Starter changes are medium effort with compatibility risk for existing generated sites. Site adoption and SSR/i18n are high effort and deployment-dependent; ship them separately after the MVP and do not promise automatic coverage of arbitrary Astro projects.

Verification and test matrix
