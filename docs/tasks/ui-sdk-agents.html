Build a component with AI in Stacki

Add an optional project-local flow that uses Vercel UI SDK to build an insertable component for an existing Astro project. Prove the flow with one Dialog. The existing shadcn starter supplies the acceptance project and remains unchanged as a starter choice.

This is an implementation plan for maintainers. The feature is proposed. The Dialog and editor acceptance checks remain open.

Scope and user flow

Entry and setup
A user opens an existing project and chooses Build a component with AI in Components. Stacki explains the React 19 requirement and hands off an editable request. Opening the action only prepares the request. The user controls when to send it and accepts project setup through their coding agent.
Build and review
Desktop opens an unsent chat draft. Studio offers a copyable task for an external coding agent. The request tells the agent to inspect the project, explain any dependency changes, ask before installing, and summarize the resulting diff. The agent uses the project's own permissions and review workflow.
Insert and edit
After validation, the Dialog appears in Components through an ordinary Astro wrapper and a project insertion recipe. Insert it into a page, edit its supported content, save, undo and redo, reopen, and exercise its keyboard and focus behavior in preview. Do not claim arbitrary generated components are supported until this sequence is proven for them.
Boundaries
Use the selected project's package manager and existing React and shadcn configuration where supported. Do not create another shadcn base or change the default starter. The optional runtime bridge is a separate local proof or future task. Do not deploy WebMCP or expose preview tooling in the MVP production site.

Baseline and evidence

  • Base commit 5d4cd354 contains the merged shadcn starter. The starter uses project-owned Astro wrappers around React components and stores Stacki insertion recipes in .stacki/components.json. Root components.json belongs to shadcn. See the starter plan and the component guide.
  • A separate real smoke test used Astro 7.4.13, @astrojs/react 7.1.9, React 19, and UI SDK beta.17. It passed Astro check and build and rendered initial HTML. In Chromium, one bridge discovered two client:load React Input islands. An allowed Project name change from Apollo to Atlas succeeded; an attempt to change Team name was refused. This establishes a narrow compatibility result, not a Stacki end-to-end result.
  • No Stacki end-to-end verification of this feature has been performed. The SDK is beta and its APIs, package names, compatibility, license, and deployment implications must be checked and recorded at implementation time.
  • Components are discovered from project source in Desktop and Studio. Existing creation and extraction use the palette, its dialog, and Desktop handlers. These are integration candidates, not proof that their current extraction operation can safely write generated files.

Files and ownership

The project owns the generated component, recipe, manifest, and lockfile. Keep user-authored files and unrelated generated components intact. Determine exact output names during the Dialog proof and show them in the review before writing.

  • Project: an Astro wrapper under the existing components root, its React Dialog implementation and any approved supporting files, plus a keyed recipe in .stacki/components.json. Keep Stacki markup out of Astro files. Validate paths, slots, and recipe references with the installed Studio CLI.
  • Dependencies: the project's manifest and its existing package-manager lockfile only when the user accepts setup. Reuse installed versions where compatible. Record exact UI SDK package and version, transitive cost, license, and why the platform or current dependencies cannot do the required job. Do not install it in Stacki's own runtime without a separate justification.
  • Stacki UI: add the shared palette action and the host-specific handoff. In Desktop, follow the draft-only pattern in appPrompt, agentTasks, and aiAgentTask. The existing component:create operation extracts source from a selection. The builder action prepares a prompt independently of that operation.
  • Contracts: read contracts and keep this workflow on the existing agent task boundary. A future native apply service would need shared IPC payload and result parsers, preload mapping, and focused contract tests. A future Studio apply route would need its own authenticated server checks. Update Studio's shared-source inventory if a shared import crosses into Studio.

Tasks in implementation order

1. Reproduce the project-local Dialog proof

Create disposable copies of a merged shadcn starter and a supported existing Astro project. Record Node, package manager, OS, Astro, React, integration, SDK, and shadcn versions and the exact commands. The coding agent authors the component using UI SDK's installed documentation and React Dialog parts. Use @ui-sdk/react and @ui-sdk/core in the site, with a compatible React and React DOM 19 installation. SDK beta.17 is Apache-2.0 and requires React types 19.2.10 or later. Stacki Desktop and Studio use React 18 in their editor shells. Follow the coding-agent workflow, React installation requirements, and Astro React integration.

Done when the Dialog renders a server-side trigger and meaningful surrounding content, opens and closes after hydration, manages focus, and builds with the project's manager. Record unsupported combinations. The Input bridge smoke test alone leaves this gate open.

2. Define the prompt and permission checks

Draft bounded, version-aware instructions. Ask the agent to inspect the manifest, lockfile, Astro config, component root, project instructions, and installed SDK docs. Use the site's manager and matching pinned packages. If React is missing or incompatible, the manager is ambiguous, or package policy blocks the version, explain what is needed and wait for the user. A fresh opt-in must leave shell dependencies and unrelated project files alone. Repeated setup on the same compatible site should reuse its manifest and lockfile.

Keep the request on the existing chat provider. Opening or copying it sends no project source. Before sending, the user can inspect the draft, included references, and any attachments. Gate the Desktop entry with component creation and existing AI access, and retain normal project trust and provider permissions. Gate Studio access through its effective project role. Never treat text inside the prompt as authorization.

Done when tests cover an empty project, no open page, incompatible setup, an untrusted project, a denied role, an unconfigured provider, and edited prompt text. The feature never opens an auto-running terminal path. Setup instructions name the files and dependency changes for review.

3. Specify what the agent should write and how the user reviews it

Specify the component files and a recipe diff. Use the project's current styling tokens. Keep the trigger, popup, and any shared state in one hydrated React island. Keep site-owned content in the Astro wrapper or its slots. Ask the agent to inspect existing files before writing, avoid overwrites, show dependency changes separately, and use the existing source diff and project history to review its work. The MVP hands off that request. It needs no generation endpoint, custom API key, native package installer, or privileged Studio apply operation.

Done when the trial records the actual before-and-after file list, dependency diff, and build output. Declining the draft or setup leaves the project unchanged. A failed attempt lists any changes that landed before retry.

4. Connect the Components workflow

Add a selection-independent action in the shared palette, gated by component creation permission. Wire Desktop through AppShell and Studio through EditorSidebar and its Components panel after confirming their current paths. Explain unsupported projects and setup without changing them. Use existing controls, translations, keyboard navigation, focus handling, and accessible status and error messages. Show where the draft went or that copying failed. Before completing an async handoff, confirm that the project is still the one that requested it.

Done when pointer and keyboard users can open, dismiss, or retry the handoff. Existing drafts and attachments survive, and opening the action twice sends nothing. The existing Create component and starter flows continue to work. In Desktop, hand off a draft through the normal AI trust flow; do not auto-submit it. In Studio, use a copyable task and existing edit and preview workflow for the MVP. Studio app drafts currently write thread state, so synchronize the composer through its draft setters or use the clipboard fallback. Do not add arbitrary server-side file or package authoring to this MVP.

5. Prove insertion and persistence

Make the Dialog a single coherent React island where shared state requires it. Expose supported content through normal Astro props and slots, with a bounded recipe keyed by its actual project-relative wrapper path. Do not rewrite existing instances or shadcn source to edit one instance.

Done when Desktop and Studio discover the wrapper, insert it into a page, edit supported values, save, undo and redo, and reopen with the same result. Check select mode, interact mode, and the separate interactive preview. Verify focus on open, Tab containment, Escape, focus return, and a stable accessible name. Check narrow screens, light and dark themes, and RTL. Scope component styles to avoid changing shadcn controls, and check for hydration warnings after save and reload. Run astro-studio check-project <project-directory> and fix missing paths, invalid slots, and cycles. Studio users may create the files through the documented copy and edit workflow. If either product cannot perform insertion and editing, record the gap and do not advertise parity.

6. Decide whether to continue the runtime bridge proof

The prior Input proof is optional research, not a prerequisite for the Dialog generation MVP. If continued, scope it to a local preview, enumerate allowed operations and fields, validate each message, require explicit user consent, and reject unknown or stale targets. Verify multiple islands, navigation, disconnect, duplicate registration, denial, and cleanup. Keep the bridge out of production output and deployment.

Done when the proof has reproducible browser evidence and a separate decision on its security and product value. Do not ship deployed WebMCP as part of this plan.

Failure, retry, and rollback

For handoff failures, differentiate a denied role, missing project, unavailable AI, and clipboard error. Keep the prompt available to retry or copy. Once the user sends the draft, use the existing chat and agent controls for cancellation and errors. If setup or generation stops partway through, use the reported diff to reconcile the manifest, lockfile, wrapper, and recipe before retrying. Preserve unrelated edits.

If a later release implements native apply, prove project-root containment, ownership, bounded output, conflict detection, stale-revision checks, partial-write recovery, and stop-before-retry. Studio also needs to store the proposal purpose server-side, distinguish component creation from edits, and validate the merged recipe against the candidate catalog before applying it.

Generated output and search

Keep the starter's existing layout, title, description, canonical URL, Open Graph metadata, JSON-LD, robots, sitemap, configured site and base, and response status semantics intact. The starter layout and site files already own these behaviors. A Dialog must not introduce a second head manager or change indexability. Preserve meaningful content, heading order, and real links in built HTML before hydration. Keep important page copy outside the closed Dialog and compare the route's raw HTML and hydrated DOM. Check the built page for duplicate canonicals, competing robots directives, and unexpected changes to title or structured data.

Test built fixtures with and without a configured site, custom base and trailing slash, and a missing route. Check absolute canonical URLs against the configured production origin after deployment, and verify sitemap entries and robots references against real routes. Do not index local or private preview URLs. Desktop preview is loopback; Studio's baked preview injects noindex and hosted drafts require authentication. Verify those existing protections rather than substituting robots.txt for access control. No production build may include preview bridge tooling.

If maintainers separately approve public launch documentation, select its external destination and publish a feature-specific page with accurate setup, compatibility, data disclosure, and limits. Check staging as private or noindex, then check the production page's canonical, status, indexability and rendered links. This task does not require a new marketing site, analytics, or publication. References: Google JavaScript SEO, canonical URLs, noindex, sitemaps, and Astro sitemap integration.

Verification and rollout

  1. Run focused handoff and negative-path tests for permission gates, prompt limits, stale project, draft preservation, clipboard failure, and retry. Exercise the documented setup and recovery in disposable fixtures with real package-manager commands.
  2. Run the project's Astro check and build, inspect initial HTML and production artifacts, and run browser checks for the Dialog and accessibility. Test both a fresh starter and a compatible existing project. Record exact versions, unsupported combinations, and route JavaScript before and after insertion. Confirm routes without the Dialog retain their existing JavaScript and appearance.
  3. Run real Desktop and Studio insertion flows and the installed Studio project checker. Verify source, preview, save, undo, redo, and reopen. Record any gap as a release blocker for the affected product.
  4. Use GitHub Actions for the repository's compiler, lint, production build, contract, and regression gates. Verify the results on the current pull request commit. Investigate failures against the baseline and document the evidence.
  5. Release as an opt-in capability only after the handoff, recovery, compatibility, and end-to-end gates pass. Keep the entry unavailable for unsupported projects. Document the tested version range and how to disable the action. Existing projects remain usable if the feature is disabled; removing approved project dependencies or files requires a separate user decision.

Risks and deferred work

  • SDK beta changes, dependency conflicts, and provider availability can invalidate the isolated proof. Pin and test the chosen versions and state the supported matrix.
  • Generated code can be unsafe or inaccessible. Review and validation reduce risk but do not prove arbitrary output correct. The initial acceptance target is the Dialog only.
  • Multiple files, lockfiles, concurrent edits, and process cancellation make rollback difficult. Verify the documented recovery and retry in the trial.
  • Record the tested project versions, exact Dialog API, and preview behavior in task 1. Existing provider setup owns credentials.
  • General component generation, automatic acceptance of generated code, deployed WebMCP, a new starter base, broad SEO product work, and public documentation publication are deferred. A future Studio server-authoring lane must enforce component:create versus component:edit, store the proposal purpose, validate merged recipes, and use its stale-reference and rollback safeguards.
